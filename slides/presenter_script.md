# Presenter Script (5-slide video, ~5 minutes)

Read at a relaxed pace; each slide is timed for roughly 60 seconds. Pause one beat at every paragraph break before advancing the slide.

[~60s] SLIDE 1
Our project is churn-hpc. We ran a small deep-learning workload through a production AI-infrastructure pipeline to find the real bottleneck. The dataset is Churn_Dataset.csv: 5,000 telecom customers, 16 numeric features, 341 KB, 14% churn rate. The model is a small MLP, 128-64-32, in JAX/Flax and PyTorch, getting 91 to 94% test accuracy versus an 86% majority-class baseline. The point is the dataset is tiny, so every hardware tier is oversized. This exposes fixed infrastructure costs like kernel dispatch, thread sync, and compile time instead of burying them. We asked which hardware rung this workload needs, and what actually limits it. We measured 17 configs across five architectures: Apple M4 CPU and GPU, arm64 Grace, x86 Xeon, NVIDIA GH200, and TPU v5e, on a local laptop, the Stanford hpcc cluster, and Google Cloud. To test this accurately, we had to standardize our environments first.

[~60s] SLIDE 2
We built immutable environments so nothing is ever installed on our nodes. We used pinned Docker images. On SLURM, that exact pinned PyTorch image runs as a read-only 3.2 GB Apptainer .sif file. On Kubernetes, pinned wheels bootstrap inside ephemeral containers. For orchestration, we ran on-prem Kubernetes jobs with exact CPU, memory, and GPU requests. We also provisioned a GKE Autopilot TPU v5e 2x2 slice on demand from a nodeSelector, and installed a single-node SLURM controller ourselves on the Stanford head node with slurmctld, slurmd, and munge. For storage, the dataset is staged once from shared storage to node-local scratch, then to RAM, then to device memory. The training loop never touches shared storage. For compilation, JAX/XLA fuses the forward, backward, and the Adam update into one compiled step, while PyTorch runs the GPU path. With the infrastructure locked down, we needed a way to measure the truth.

[~60s] SLIDE 3
Our measurement strategy focused entirely on honest accounting. We captured per-step wall-clock timing with forced device synchronization, so step times are honest. The first compiled step was timed separately to isolate compile overhead. That overhead was 0.16 seconds for XLA on the CPU, 0.41 seconds on the TPU, and 0.01 seconds for eager PyTorch. In the background, a psutil sampler tracked whole-node CPU percent and memory. We also ran a 1 Hz nvidia-smi trace on the cluster GPU job. Every run emits one JSON record, and all charts regenerate from committed data. We trained for 400 epochs per config. When we finally looked at the data across those 400 epochs, the scaling results completely broke our assumptions.

[~60s] SLIDE 4
Core scaling failed everywhere we tried it. The M4 10 cores versus 1 core was 1.00x. The Xeon 32 cores reached 99.7% node utilization yet ran slower than 1 core, getting 107K versus 114K samples per second. Grace 32 cores ran 7x slower than 1 core. Accelerators at default batch 512 lost too. The M4 GPU was 0.42x its own CPU. The NVIDIA GH200 480GB managed 92.6K samples per second, about one tenth of the laptop CPU, at 6% peak GPU utilization and 0.9% of its 97 GB HBM. Batch size was the only lever that worked. The M4 GPU went 5.15x faster from batch 512 to 4000, hitting 2.01M samples per second. The TPU v5e step time stayed constant at 2.1 ms from batch 512 to 16,384, so throughput scaled 17x to 3.22M samples per second, the best number in the study, with accuracy unchanged at 0.919. These hardware failures all point to a single architectural root cause.

[~60s] SLIDE 5
The bottleneck is a fixed per-step dispatch and launch cost on the host, which we confirmed on five architectures. Lesson one is that utilization is not throughput. The Xeon burned all 32 cores at 99.7% to go slower than one. Lesson two is to grow the batch before you grow the hardware. On cost, the TPU wins throughput 3.4x over the best CPU but costs roughly 10x per node-hour. Below about a million rows, one CPU node with XLA compilation is the cost-optimal home for a single job. Accelerators earn their price on batched or parallel work, like hyperparameter sweeps. We falsified three obvious upgrades: more cores, a GPU at default batch, and bfloat16 on CPU with less than a minute of total compute. The whole study regenerates from the repo with one script. Thanks for watching.
